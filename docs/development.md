# Development

## Commands

```sh
bun install
bun run tauri dev          # desktop app
bun run tauri android dev  # Android on a connected phone (see "Android toolchain" below)
bun run android:apk        # installable arm64 APK in src-tauri/gen/android/app/build/outputs/apk/
bun run relay              # local sync relay on :8787
bun run test:rust          # app + relay tests, including end-to-end sync against a real relay
bun run test:e2e           # Playwright UI tests against a mocked backend
bun run dev:web            # the web version on :1420, with `bun run relay` running
bun run build:web          # the web version, into sync-server/web for the relay to serve
bun run test:web           # the built web version against a real relay (Playwright)
bun run verify             # everything CI runs
```

Only one copy of the desktop app runs at a time: launching another (or opening an `ezcount://` link) hands over to the running one. So if `bun run tauri dev` quits right after `Running target\debug\ezcount.exe`, close the ezcount window that's already open.

Dev builds (`tauri dev`) use the relay at `http://localhost:8787`, and `VITE_EZCOUNT_SERVER` sets another one at build time. On the login screen, **Change** under the form picks another relay; the app remembers it.

## Git hooks and CI

Git hooks ([lefthook](https://lefthook.dev), installed by `bun install`):

- **pre-commit** regenerates `src/bindings.ts` when Rust changes, then in parallel: rustfmt, Biome and Prettier (all fix and re-stage), clippy on the touched crate, and `svelte-check`. Biome lints everything and formats TypeScript, CSS and JSON; Prettier formats the `.svelte` files, whose templates Biome can't format reliably yet. Only jobs whose files are staged run.
- **commit-msg** requires a [Conventional Commits](https://www.conventionalcommits.org) subject (`feat(ui): …`, `fix: …`).
- **pre-push** runs the Rust tests and the Playwright suite.

Skip them once with `LEFTHOOK=0`. CI (`.github/workflows/ci.yml`) runs the same checks on Linux and builds the relay image. Dependabot proposes weekly updates, waiting 7 days after each release.

## Interface

Svelte 5 with [shadcn-svelte](https://shadcn-svelte.com) (bits-ui) on Tailwind v4. `src/components/ui/` is generated by the shadcn-svelte CLI and not linted or formatted; add more components with `bunx shadcn-svelte@latest add <name>`. Theme colors, including the `positive`/`negative` money colors, are in `src/styles.css`. App-wide state (account, groups, navigation, open dialogs) lives in `src/lib/state/*.svelte.ts`.

Text lives in `src/lib/i18n/en.ts` and `fr.ts`, read with `t("key")`; amounts and dates are written the way the language does (`1 234,50 €`, `€1,234.50`). To add a language, copy `fr.ts`, translate it and list it in `index.svelte.ts`; `backend.ts` translates the messages the Rust core writes in English.

## Test builds for phones and Linux

Every push to `main` that touches the app runs `.github/workflows/packages.yml` (run it by hand from the Actions tab otherwise), which builds:

- **`ezcount-android`**: an optimized APK for arm64 phones. It is somewhat larger than a local `bun run android:apk` (about 15 MB), because CI skips link-time optimization to build faster,
- **`ezcount-linux`**: a `.deb` and an `.AppImage`.

Download them from the run's **Artifacts** section on GitHub. To install the APK, enable USB debugging on the phone and run `adb install -r <file>.apk`, or copy the file to the phone and open it. CI signs every APK with the private release key (below), so a new one installs over the previous one and keeps the app's data.

The app uses the official relay, `https://ezcount-relay.fly.dev`, unless the login screen's **Change** link says otherwise. To build packages for another relay by default, set the repository variable `EZCOUNT_SERVER` (Settings → Secrets and variables → Actions → Variables) to its URL.

To try the phone on your home network without deploying anything, run `bun run relay` on your computer, allow it through the firewall, and use `http://<computer's LAN IP>:8787` as the server on both devices. `localhost` on the phone means the phone itself.

## Signing key

Android installs an update only if it's signed with the same key as the installed app, and the relay's App Links trust one key. So whoever holds the key can publish an "update" that reads everything the app stores. Two keys:

- **The release key** signs every APK that leaves your devices: CI builds and releases. It's private, created with `keytool` (PKCS12, alias `ezcount`, 4096-bit RSA) and kept outside the repository, e.g. in `%USERPROFILE%\.ezcount-signing\`. CI reads it from two repository secrets: `ANDROID_RELEASE_KEYSTORE` (the `.p12` file in base64) and `ANDROID_RELEASE_KEYSTORE_PASSWORD`; without them the Android build fails on purpose. Its SHA-256 fingerprint is in `sync-server/fly.toml` for App Links. **Back up the key and its password** (a password manager takes both): without them, no update can ever install over the app again, and every user has to uninstall it (their data comes back from the relay when they log in).
- **The test key**, `src-tauri/gen/android/app/debug.keystore`, is committed and public. Local builds use it unless `EZCOUNT_RELEASE_KEYSTORE` and `EZCOUNT_RELEASE_KEYSTORE_PASSWORD` point at the release key. Keep test-key builds on your own devices. They get no App Links (invite links open the `/join` page first), and a phone can't switch between the two keys without uninstalling the app.

## Releases

Write what changed for users under `## Unreleased` in [CHANGELOG.md](../CHANGELOG.md) as you go. Then:

```sh
bun run release 0.2.0     # sets the version everywhere, dates the changelog, commits "chore(release): v0.2.0", tags v0.2.0
git push --follow-tags
```

The tag starts `.github/workflows/release.yml`: it checks the tag matches every manifest, builds the APK and Linux packages with full optimization, deploys the relay to Fly.io, and once both succeeded creates the GitHub release with the packages attached and that version's changelog section as its notes. If a step fails, nothing is published; fix it, delete the tag (`git tag -d v0.2.0 && git push origin :v0.2.0`) and release again.

The relay must keep working with the previous app versions, since phones don't all update at once: only add to its API, never change or remove what's there.

## Upgrading Tauri

Tauri's Rust crates and npm packages must be on the same major.minor version, or the Tauri CLI refuses to build in CI. So they are pinned to one minor (`tauri = "2.12"` in `src-tauri/Cargo.toml`, `~2.12` in `package.json`), Dependabot only proposes patch updates for them, and `bun run check:tauri` (run by CI and the pre-commit hook) compares both lock files. To move to a new minor, say 2.13, change both sides in one commit:

```sh
bun add @tauri-apps/api@~2.13.0 @tauri-apps/plugin-opener@~2.x.0
bun add -d @tauri-apps/cli@~2.13.0
# src-tauri/Cargo.toml: tauri = "2.13" (both entries), plus matching tauri-build / tauri-plugin-opener
cargo update --manifest-path src-tauri/Cargo.toml -p tauri -p tauri-build -p tauri-plugin-opener
bun run check:tauri
```

## Android toolchain

Building Android locally needs, besides Rust and Bun:

- JDK 17, the Android SDK (platform 36, build-tools) and the NDK, found through the `JAVA_HOME`, `ANDROID_HOME` and `NDK_HOME` environment variables,
- `rustup target add aarch64-linux-android`,
- on Windows, **Developer Mode** (Settings → System → For developers), because Tauri symlinks the Rust library into the Android project.

Keep `GRADLE_USER_HOME` on the same drive as the project if you can; `gradle.properties` already works around the Kotlin daemon's cross-drive failure.

## The web version

The browser runs the app's Rust core itself, compiled to WebAssembly (`web/`), so groups stay end-to-end encrypted as in the apps. The core runs in a Web Worker (`src/web/worker.ts`), keeping its SQLite database in the origin's private file system (OPFS), and `src/web/install.ts` stands in for Tauri: the Svelte app calls the same commands, with the same JSON, as in the desktop and Android apps (`core/src/api.rs` routes them by name).

The relay serves it, from the same address as its API: open `https://<relay>/`. Building it needs, besides Bun and Rust:

- the WebAssembly target: `rustup target add wasm32-unknown-unknown`,
- the wasm-bindgen CLI at the version in `web/Cargo.lock`: `cargo install wasm-bindgen-cli --version <version> --locked` (`bun run build:wasm` says which),
- a clang that compiles to WebAssembly, for SQLite: LLVM's, or on Windows the Android NDK's, found through `NDK_HOME`.

`bun run build:web` writes it to `sync-server/web`, which the relay serves when `EZCOUNT_WEB_DIR` points there (the Docker image includes it if it was built first). Releases build and deploy it with the relay.

What differs from the apps:

- **One tab at a time:** the database can't be shared between tabs. A second tab says so, and hands over the invite it was opened with.
- **Trust in the server:** a website's code comes from the server on every visit, so whoever controls the relay could serve code that reads your data (see [security.md](security.md)).
- **Browser storage can be cleared**, by the user or, for sites not visited in a while, by Safari. Everything synced comes back on the next login; unsynced changes would be lost.
- No QR code scanning, and only the relay that serves the page (another one would need CORS).
